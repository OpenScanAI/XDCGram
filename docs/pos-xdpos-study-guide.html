Part I

Proof of Stake, from first principles

Before XDPoS makes sense, generic PoS has to make sense — what problem it solves, who the actors are, and what "finality" actually means. Each module below opens with plain-English reasoning, then the term glossary.

01

Why Proof of Stake Exists

Proof of Work (PoW) secures a chain by making block production expensive — miners burn real electricity racing to find a hash below a target. That cost is the security: rewriting history means out-spending the entire honest network's energy bill. PoS keeps the same idea — attacking the chain must cost more than you could gain — but replaces "burn energy" with "burn capital you already own and can lose." That single substitution removes the environmental cost and, more importantly, gives the protocol a lever it never had before: it can now confiscate the attacker's stake (slashing), not just make the attack expensive to attempt.

Problems with Proof of Work

  • Energy consumption: Security scales with hash rate, and hash rate scales with electricity. Bitcoin's annual draw is comparable to a mid-sized country — that cost is paid every single day, forever, just to keep the chain safe, whether or not anyone is attacking it.
  • Mining centralization: Because rewards are proportional to hash rate and variance is brutal for small miners, rational actors join pools. A handful of pools have at various points controlled >50% of Bitcoin's hash rate between them — the "decentralized" security model concentrates into a few operators.
  • ASIC monopoly: Once mining becomes profitable at scale, general-purpose hardware (CPUs/GPUs) gets out-competed by application-specific chips. A few fabricators (historically dominated by Bitmain) end up gatekeeping who can even participate profitably.
  • Scalability problems: Block time and block size are both constrained by propagation — if blocks are too big or too frequent, slower miners keep losing the race and get orphaned, which pushes toward centralization. This caps throughput independent of demand.
  • Environmental concerns: Regulatory and public pressure (e.g., China's 2021 mining ban) directly threatens PoW networks in ways that don't apply to PoS, since PoS's energy footprint is close to that of a normal data center.
  • Economic incentives: Miners must sell a portion of block rewards to cover hardware amortization and power bills, creating structural sell pressure on the token regardless of market sentiment.
  • Bitcoin's own limits: ~7 transactions/second, 10-minute average block time, and probabilistic (never absolute) finality — a transaction is only "safe" after several confirmations, and technically can still be reversed with enough hash power.

History of PoS

  • Peercoin (2012): The first live PoS implementation, but it was hybrid — PoW created new coins, PoS ("minting") secured the chain using coin age (balance × time held) to weight who could mint the next block. It proved stake-weighted block production could work at all.
  • Casper (2015 onward): Ethereum research's name for its PoS research program, which split into two competing designs — Casper FFG (a finality gadget layered on top of a separate proposal mechanism, which is what shipped) and Casper CBC (correct-by-construction, a more theoretical BFT-family design that didn't ship).
  • The Merge (September 15, 2022): Ethereum's execution layer (the old PoW chain) was joined to the already-running Beacon Chain (PoS, live since Dec 2020), switching consensus from mining to validating in a single block without a hard restart of state.
  • Evolution: Early PoS designs were "chain-based" (closer to Nakamoto-style longest-chain, just with stake instead of hash power). Modern designs (Ethereum, Tendermint, XDPoS v2) are epoch/round-based with explicit BFT-style voting and provable finality, not probabilistic finality.

02

Proof of Stake Fundamentals

The core mechanic: instead of "whoever finds the hash first proposes the block," it's "whoever the protocol deterministically-but-unpredictably selects, weighted by locked stake, proposes the block — and a committee of other stakers has to vote on it before it's considered settled."

  • Proof of Stake: A consensus mechanism where the right to propose and the weight of your vote on validity are both proportional to economic stake locked as collateral, which can be destroyed (slashed) for provable misbehavior.
  • Stake: Native tokens locked in a deposit/staking contract. It's simultaneously your ticket to participate and your bond against misbehaving.
  • Validator: The role (not necessarily a person) that runs the software, proposes blocks on its turn, and attests (votes) on other proposers' blocks every epoch.
  • Consensus: The rules by which every honest node ends up agreeing on the same ordered history, even though messages arrive at different times and some participants may be faulty or malicious.
  • Epoch: A fixed batch of slots (32 in Ethereum, ~6.4 minutes; 900 blocks in XDPoS v2, ~30 minutes) that acts as the checkpoint/accounting boundary — rewards, validator set changes, and finality all happen at epoch granularity.
  • Slot: The fixed time window in which exactly one proposer is allowed to publish a block (12s on Ethereum; 2s in this XDPoS devnet). A slot can be empty if the assigned proposer is offline or times out.
  • Committee: A pseudo-randomly sampled subset of the full validator set assigned to vote in a given slot — this exists so not every validator has to vote on every single block, which would not scale bandwidth-wise.
  • Beacon Chain: Ethereum's dedicated consensus-only chain — it doesn't run the EVM or hold user balances; it only tracks the validator registry, attestations, randomness, and finality, and tells the execution layer which blocks are canonical.
  • Validator set: The current registry of everyone with stake deposited, in whatever lifecycle state (pending/active/exiting).
  • Active validators: Currently eligible to be selected as proposer and required to attest every epoch.
  • Pending validators: Have deposited stake but are still in the activation queue — this queue exists deliberately, see churn limit below.
  • Exited validators: Have left the active set (voluntarily or by force) and are in or past the withdrawal process.
  • Churn limit: A hard cap on how many validators can enter or leave the active set per epoch. Without it, a huge coordinated exit could shrink the validator set instantly, which is dangerous both for liveness and because it would let an attacker "test" different validator-set compositions cheaply (a variant of stake-grinding).
03

Validator Architecture

A "validator" is not one program — on Ethereum it's the coordination of three separate pieces of software (or two, if you count consensus+execution as one integrated stack, which is what XDPoS actually does). Understanding the split matters because it explains why XDPoS's single-binary design (Part II) is architecturally simpler.

  • Validator lifecycle: deposit → pending (queued) → active (proposing/attesting) → exiting (voluntary or forced) → withdrawable (funds unlocked).
  • Validator keys: A BLS keypair for signing attestations/proposals (chosen because BLS signatures can be aggregated — thousands of votes compress into one signature), plus separate withdrawal credentials controlling where funds go on exit.
  • Validator client: The process that actually holds the signing key and produces attestations/block signatures on schedule (Lighthouse, Prysm, Teku, Nimbus, Lodestar). This is the only piece that needs the private key.
  • Consensus client: Runs Beacon Chain state transition, fork choice, gossip networking, and tells the validator client when it's due to act. Same binaries as above typically bundle both roles.
  • Execution client: Runs the EVM, mempool, and state (Geth, Nethermind, Erigon, Besu) — it has no concept of "validators" or "epochs" at all; it just executes transactions when told to by the consensus client via the Engine API.
  • Withdrawal credentials: Prefix 0x00 means funds return to a BLS key (older, requires a manual one-time upgrade to withdraw); prefix 0x01 points directly at an execution-layer address and enables automatic partial withdrawals.
  • Validator registration: A 32 ETH transaction to the deposit contract on the execution layer, carrying the validator's BLS pubkey, withdrawal credentials, and a signature proving key ownership.
  • Activation: After the deposit is observed and finalized, the validator enters the pending queue and is activated once its turn comes up under the churn limit.
  • Exit — voluntary: The operator signs an exit message; no penalty beyond forgone future rewards.
  • Exit — forced: The protocol itself ejects a validator, typically for an effective balance that's dropped too low (from accumulated penalties) — this is a safety valve, not a punishment on its own.
  • Withdrawal queue: Exits are rate-limited by the same churn logic as activations, so a mass exit still drains gradually rather than instantly destabilizing the validator set.
  • Partial withdrawal: Automatic sweep of any balance above 32 ETH (accumulated rewards) to the withdrawal address, without touching the validator's active status.
  • Full withdrawal: Only happens after a completed exit — the entire remaining balance is swept out and the validator is permanently retired.

04

Staking

"Staking" is really a spectrum of trade-offs between how much control you keep and how much capital/technical effort you need. XDPoS's masternode model (Part II) is closest to delegated staking — token holders vote for a fixed number of masternode operators rather than everyone running their own validator.

  • Native/solo staking: You personally run validator software and hold the full minimum deposit (32 ETH). Maximum control, maximum responsibility — if your node goes offline you eat the inactivity penalty yourself.
  • Delegated staking: You don't run anything; you delegate your tokens' voting weight to an operator you trust, who runs the infrastructure and shares rewards minus a commission (this is structurally what XDPoS masternode voting is).
  • Liquid staking: A protocol stakes on your behalf and mints a tradeable receipt token (e.g., stETH) representing your claim — you keep liquidity while still earning yield, at the cost of trusting the protocol's smart contracts and validator set.
  • Pool staking: Multiple people's sub-minimum deposits are pooled to collectively reach the 32 ETH requirement (e.g., Rocket Pool minipools) — this exists specifically because 32 ETH is too high a barrier for most individuals.
  • Custodial staking: An exchange holds your private keys and stakes for you (Coinbase, Binance) — convenient, but you don't control the keys, which reintroduces counterparty risk the whole point of self-custody was meant to remove.
  • Non-custodial staking: You keep signing/withdrawal control; you only delegate the staking duty, not custody of the asset.

Ethereum PoS Architecture

Post-Merge Ethereum is deliberately split into two independently-replaceable layers that talk over a minimal local API. This is the architectural choice XDPoS explicitly does not make — see Part II for why a single-binary design was chosen instead for a permissioned network.

  • Execution Layer (EL): Owns the EVM, account state, mempool, and receipts. From the EL's point of view, PoS doesn't exist — it just executes whatever block body the consensus layer hands it.
  • Consensus Layer (CL) / Beacon Chain: Owns validator registry, committees, attestations, randomness (RANDAO), and finality. It decides which execution payload is canonical, but never executes a transaction itself.
  • Engine API: A local, authenticated JSON-RPC interface (over the loopback interface, secured with a JWT secret) that the CL uses to hand the EL a new payload to execute/validate, and to ask "what's the current head."

Why this matters for XDPoS

The EL/CL split exists mainly so Ethereum's huge, already-battle-tested EVM execution engine didn't have to be rewritten to add PoS — consensus was bolted on as a separate process. XDPoS never had that legacy constraint: it forked go-ethereum directly and wired the consensus engine straight into the same binary via geth's pluggable consensus.Engine interface (the same interface point used for Clique/PoA), so there's one process, one datadir, one RPC port doing both jobs.

Consensus

"Consensus algorithm" is really answering one question: when message delivery timing is unpredictable and some participants might lie, how do independent nodes end up agreeing on one canonical history? Different families answer it differently.

  • Byzantine Fault Tolerance (BFT): A family of protocols that tolerate up to some fraction of participants behaving arbitrarily (not just crashing, but actively lying) and still reach agreement.
  • PBFT: The classical practical BFT protocol (Castro & Liskov, 1999) — three phases (pre-prepare, prepare, commit), each requiring a 2/3+ quorum of signed messages before moving on. Most modern blockchain BFT variants (Tendermint, XDPoS v2) are descendants of this idea.
  • Tendermint: Cosmos SDK's consensus engine — round-based BFT with instant, deterministic finality (a block is final the moment it's committed, no "wait N confirmations").
  • Casper FFG: Ethereum's finality gadget — not a full consensus protocol on its own, but an overlay that periodically finalizes checkpoints proposed by a separate chain-based proposal mechanism (LMD GHOST).
  • LMD GHOST: The fork-choice rule that decides which chain tip is "head" between finalization events.
  • Nakamoto consensus: The original longest/heaviest-chain rule (PoW Bitcoin) — no explicit voting, agreement emerges probabilistically from everyone extending what they believe is the heaviest valid chain.
  • Finality: The point past which a block is guaranteed (under the protocol's fault-tolerance assumption) never to be reverted. PoW only gives probabilistic finality; BFT-style PoS (Tendermint, XDPoS v2, Ethereum after 2 epochs) gives absolute finality.
  • Fork choice rule: The deterministic algorithm every node runs locally to pick "the" canonical head when it sees competing chains/blocks.
07

Byzantine Fault Tolerance, in detail

The name comes from the "Byzantine Generals Problem" (Lamport, Shostak, Pease, 1982): several generals surrounding a city must agree unanimously to attack or retreat, communicating only via messengers who might be traitors or simply too slow. The maths behind BFT protocols is the maths of solving that problem with cryptographic signatures instead of trusted messengers.

  • Honest majority assumption: BFT-style PoS protocols are safe as long as more than 2/3 of stake-weighted voting power is honest (not just >50% — the extra margin is needed because with exactly 2/3, an attacker controlling the remaining 1/3 could equivocate and still cause two different quorums to form).
  • Fault tolerance (3f+1 rule): To tolerate f Byzantine (arbitrarily malicious) nodes safely, classical BFT needs at least 3f+1 total participants — this is why validator/masternode counts are usually chosen to be one more than a multiple of 3 in principle (in practice rounded to convenient numbers like 108).
  • Safety: The guarantee that no two honest nodes ever finalize conflicting blocks at the same height — this must never break, under any network conditions, as long as the honest-majority assumption holds.
  • Liveness: The guarantee that the chain keeps producing new finalized blocks — this can stall temporarily under bad network conditions without being a safety violation (the chain pauses rather than forks).
  • Synchronous network model: Assumes a known upper bound on message delivery time — easier to build fast protocols on, but an unrealistic assumption for the open internet.
  • Asynchronous network model: No timing assumptions at all. The FLP impossibility result (Fischer–Lynch–Paterson, 1985) proves that deterministic consensus is impossible to guarantee under pure asynchrony if even one node can fail — so no real protocol assumes this.
  • Partial synchrony: The practical middle ground — messages are delivered within some bound after an unknown "global stabilization time." This is the model Ethereum and XDPoS actually design against: correct under bad conditions (safety never breaks), and fast under good conditions (liveness resumes once the network behaves).
08

Casper FFG

Casper FFG ("Friendly Finality Gadget") answers: given a chain that's already being extended by some proposal mechanism, how do we retroactively mark certain blocks as permanently irreversible?

  • Checkpoint: The first block of an epoch — the only blocks Casper FFG ever votes on (not every block, which would be too much data).
  • Justified checkpoint: A checkpoint that received attestations from validators controlling ≥2/3 of total stake, all voting for the same (source→target) checkpoint pair.
  • Finalized checkpoint: A justified checkpoint whose immediate child checkpoint is also justified — this two-hop rule is what makes finality provably irreversible: reverting it would require provably slashable double votes from at least 1/3 of all stake.
  • Epoch voting: Each active validator casts exactly one attestation per epoch (not per block), voting for a source and target checkpoint plus the current head — this is what keeps vote volume bounded regardless of how many slots exist per epoch.
  • Supermajority link: A source→target vote backed by ≥2/3 of stake — the fundamental unit Casper FFG's justification rule is built from.
  • Attestation: The signed vote itself, containing the validator's view of the current head, the source checkpoint, and the target checkpoint.
09

Fork Choice — LMD GHOST

Between finalization events, someone still has to decide "which tip do I build on right now." LMD GHOST is that rule.

  • Latest Message Driven (LMD): Only each validator's most recent attestation counts — older votes from the same validator are discarded, so the fork choice always reflects current opinion, not accumulated history.
  • Greediest Heaviest Observed SubTree (GHOST): At every fork point, walk toward the child subtree with the most cumulative attestation weight underneath it (not just weight on the immediate child block) — this correctly credits a branch even if votes are spread across several of its later blocks.
  • Combined algorithm: Start from the last justified checkpoint (the "safe" anchor Casper FFG already agreed on), then repeatedly apply the GHOST rule using only each validator's latest message to walk down to the current head.
  • Why not longest chain: Longest-chain (Nakamoto) rules are exploitable by anyone who can produce blocks fast in isolation; weight-of-attestations is exploitable only by controlling actual stake, which is exactly the resource the protocol is trying to price.

Slots & Epochs

  • Slot: 12 seconds on Ethereum, 2 seconds in this XDPoS devnet — the fixed window in which one proposer may publish exactly one block.
  • Epoch: 32 slots (~6.4 min) on Ethereum; 900 blocks (~30 min at 2s blocks) in XDPoS v2. All checkpointing, reward accounting, and (in XDPoS) masternode-set changes happen at epoch boundaries.
  • Attestation timing: Validators attest as soon as they see and validate a block, ideally within the same slot — attestations arriving very late count less toward fork-choice weight.
  • Proposer selection: On Ethereum, pseudo-random per slot, seeded by RANDAO and weighted by effective stake balance. In XDPoS it's deterministic round-robin through the current masternode list (see Part II) — a design choice that trades unpredictability for simplicity and predictable block timing.
  • Missed slot: The assigned proposer failed to publish in time — the slot goes empty and the chain simply continues at the next slot (no block is "owed" later).
  • Empty slot: A slot with no block; attestations for that slot instead vote for the most recent actual block (the "head" carries over).

11

Block Proposal Pipeline

  1. Transaction arrives at a node's RPC endpoint, gets signature-checked and nonce-checked.
  2. Mempool: Valid pending transactions sit here, gossiped to peers, ordered by fee (and, post EIP-1559, by priority fee) until picked up by a proposer.
  3. Builder (Ethereum only): Under MEV-Boost, a separate builder market constructs the most profitable possible block body and auctions it to the proposer, who doesn't see the contents — only the bid.
  4. Proposer: The validator whose turn it is this slot assembles (or accepts a builder's) execution payload.
  5. Execution payload: The EL builds the actual block body — transactions, receipts, resulting state root — and hands it back over the Engine API.
  6. Beacon block (Ethereum) / signed block (XDPoS): The CL wraps the execution payload with consensus-layer metadata (attestations, slashings, deposits/exits for Ethereum; the proposer's signature and, in XDPoS v2, the QC it's built on) and signs it.
  7. Propagation: Broadcast peer-to-peer via gossip; each receiving node independently re-validates before relaying further (never trust-and-forward blindly).
  8. Finalization: Attestations/votes accumulate until the relevant checkpoint (Ethereum) or quorum certificate (XDPoS v2) crosses the 2/3 threshold.
12

Attestations

  • Attestation: A validator's signed vote naming a source checkpoint, target checkpoint, and current head — three separate claims bundled into one signed message.
  • Committee: Each epoch's active validator set is split into committees, one per slot, so attestation load is spread evenly rather than all validators voting on every slot.
  • Aggregation: Because BLS signatures support aggregation, an entire committee's individual votes for the same message collapse into a single fixed-size aggregate signature — this is what makes tens of thousands of validators bandwidth-feasible.
  • Aggregation bits: A bitfield alongside the aggregate signature marking exactly which committee members' votes are included (since the aggregate signature itself doesn't reveal who signed).
  • Sync committee: A small (512-validator), frequently-rotated subset whose job is specifically to sign the recent chain head in a lightweight way light clients (wallets, mobile) can verify without downloading full attestation history.
13

Rewards

  • Base reward: A function of effective balance and total active stake — proportional to your share, inversely related to how many validators are competing for the same fixed issuance.
  • Proposer reward: An extra cut for successfully including other validators' attestations and sync-committee signatures in your block.
  • Attestation reward: Paid for correctly and promptly voting on source, target, and head — split into sub-rewards per correct component, and reduced the later the attestation arrives.
  • MEV / priority fee: Under EIP-1559, users pay a base fee (burned — removed from supply) plus an optional priority fee (tip) that goes entirely to the proposer, on top of any MEV a builder extracted from transaction ordering.
  • Issuance: New tokens minted specifically to pay base/attestation rewards — separate from any transaction fee revenue.
  • APR calculation: Roughly annual issuance to validators ÷ total effective stake — this is why APR drops as more people stake: the same issuance pool is split more ways.
14

Slashing

Slashing is the mechanism that makes PoS's honest-majority assumption economically enforced, not just hoped for — provable misbehavior destroys stake, not just reputation.

  • Double proposal: Signing two different blocks for the same slot — cryptographically provable (both signed messages exist) and automatically slashable.
  • Double vote: Attesting to two different target checkpoints for the same source/epoch — a direct attempt to help two conflicting forks both reach justification.
  • Surround vote: A more subtle attack — casting a new attestation whose source/target range fully encloses (or is enclosed by) an earlier attestation you made, which could otherwise help finalize two incompatible histories over time.
  • Penalty vs. slashing: A regular penalty (e.g., for being offline and missing attestations) just forfeits reward you would have earned. Slashing actively burns a portion of your existing staked balance and force-exits you.
  • Correlation penalty: The slashed amount scales with how many other validators are slashed in the same time window — a lone honest mistake costs little; a coordinated attack by many validators at once costs catastrophically more, specifically to deter cartel-style attacks.
  • Slashing protection: Local database validator clients keep to refuse ever re-signing something that could constitute a slashable double-sign, even after a crash/restart — critical when migrating a validator between machines.
  • Inactivity leak: If the chain goes more than ~4 epochs without finalizing (e.g., mass outage), offline validators start losing stake at an accelerating rate until the online minority's relative share crosses back above 2/3 — a self-healing mechanism to restore finality without a hard fork.
15

Security — Attack Classes

  • 51%/majority attack: Controlling enough stake (or hash power in PoW) to dictate the canonical chain — in BFT-style PoS this specifically means >1/3 to break liveness, or >2/3 to break safety.
  • Nothing-at-stake: An early theoretical PoS flaw — since voting is nearly free, why not vote on every competing fork to guarantee you're rewarded whichever wins? Slashing for double-voting is the direct fix.
  • Long-range attack: An attacker acquires old (no-longer-staked) validator keys and rewrites history from far in the past, since old keys have nothing left to lose. Countered by weak subjectivity checkpoints — clients trust a recent, socially-agreed checkpoint rather than validating from genesis blindly.
  • Sybil attack: Creating many fake identities to gain disproportionate influence — neutralized in PoS because influence is priced in stake, not identity count.
  • Replay attack: Rebroadcasting a valid signed transaction/message from one context (chain, epoch) in another where it would also validate — prevented with chain IDs and domain-separated signatures.
  • Equivocation: The general term for signing conflicting messages (covers double proposal and double vote) — always slashable by design.
  • Stake grinding: Trying to bias the randomness source that selects future proposers/committees in your favor — mitigated by using unbiasable randomness (RANDAO + VDF research, or verifiable randomness in general).
  • Censorship: A proposer/committee excludes specific valid transactions — mitigated by proposer-builder separation and inclusion lists research, though it's an open problem area.
  • Validator collusion: Coordinated cartels acting together — correlation penalties specifically punish this harder than independent honest mistakes.
  • MEV / time-bandit attacks: Reorganizing recent blocks specifically to capture a lucrative MEV opportunity that appeared — mitigated by making reorgs progressively more expensive the deeper they'd need to go.
  • DoS: Flooding a node/network with junk traffic to degrade liveness — mitigated with peer scoring, rate limiting, and requiring proof-of-stake-weighted priority for gossip.

Gas System

Gas is the EVM's way of pricing computation so infinite loops can't stall the network for free — every opcode costs a fixed amount of gas, and a transaction dies (reverting all state changes except nonce/fee deduction) if it runs out.

  • Gas units: An abstract cost unit — 1 gas is not 1 wei; it's a fixed "amount of work," priced separately.
  • Gas price / gas price bidding (pre-1559): How many wei you pay per gas unit — historically a first-price auction, which caused unpredictable fee spikes.
  • Gas limit (per tx): The maximum gas the sender authorizes this transaction to consume — protects the sender from an unbounded bill if something loops unexpectedly.
  • Block gas limit: The total gas cap for all transactions in one block — this is the real throughput bottleneck of the EVM, not block size in bytes.
  • Base fee (EIP-1559): An algorithmically-adjusted, per-block fee that's burned — rises when the previous block was over the target gas usage, falls when under, targeting 50% block fullness on average.
  • Priority fee (tip): On top of the base fee, paid directly to the proposer as an incentive to include your transaction promptly or preferentially.
  • Max fee: The absolute cap you're willing to pay per gas (base + priority combined); if base fee alone exceeds it, your transaction simply won't be included yet.
  • Fee burning: The base fee is destroyed, not paid to anyone — this makes ETH's supply deflationary during periods of high usage, unlike the old flat fee-to-miner model.
  • Gas estimation: Wallets simulate a transaction against current state to predict its gas cost before you sign, since gas usage depends on the exact code path taken (branches, storage slots touched).
  • Out of gas: Execution halts mid-way, all state changes revert, but the gas already consumed is still charged (this is what stops spam — failed attacks still cost the attacker).
  • Refunds: A small gas rebate for certain state-clearing operations (e.g., setting a storage slot back to zero) — capped to prevent gas-refund gaming exploits seen historically.
  • Intrinsic gas: The flat baseline cost every transaction pays just for existing (21000 gas on Ethereum) plus per-byte calldata costs, before any opcode even runs.
  • Opcode / storage / memory gas: Different resource classes are priced very differently — a simple arithmetic opcode costs a few gas; a fresh SSTORE (writing to a previously-empty storage slot) costs thousands, because permanent state growth is the scarcest, most expensive resource in the system (every full node must store it forever).
17

Transactions

  • Transaction structure: nonce, gas price/fee fields, gas limit, to-address (or empty for contract creation), value, data (calldata or init code), chain ID, and a signature (v, r, s).
  • Nonce: A strictly increasing per-account counter — the primary defense against replaying or reordering a sender's own transactions.
  • Signature: ECDSA over secp256k1 in Ethereum-family chains; proves the sender authorized exactly this transaction content.
  • Chain ID: Embedded in the signed payload (EIP-155) specifically so a transaction valid on one network can't be replayed on another (e.g., mainnet vs. a private XDPoS devnet sharing similar tooling).
  • RLP encoding: Recursive Length Prefix — the compact binary serialization format Ethereum-family chains use for transactions, blocks, and the state/receipt tries, chosen for being simple and unambiguous to decode.
  • Transaction hash: Keccak256 of the RLP-encoded signed transaction — the canonical unique ID you look up in an explorer.
  • Receipt: Post-execution record — status (success/revert), gas used, logs emitted, and a bloom filter — stored separately from the transaction itself.
  • Logs / events: Arbitrary data a contract emits during execution (via LOG opcodes / Solidity's event) — the primary way off-chain applications know something happened on-chain without re-simulating every transaction.
  • Bloom filter: A probabilistic per-block/per-receipt data structure letting a light client quickly check "could this block contain a log matching X topic" without downloading and scanning every log.
18

Cryptography a Developer Must Know

  • SHA-256: Used by Bitcoin's PoW and various signature schemes — a 256-bit general-purpose cryptographic hash.
  • Keccak256: The hash function Ethereum-family chains use everywhere — addresses, storage slots, transaction/state hashing (note: this predates and differs slightly from the later standardized SHA-3).
  • ECDSA: Elliptic Curve Digital Signature Algorithm over secp256k1 — the signature scheme securing Ethereum-family accounts and transactions; not aggregatable, which is exactly why BLS was introduced for validator-scale voting.
  • BLS signatures: A pairing-based scheme whose signatures can be aggregated into one fixed-size signature regardless of how many signers — the enabling technology behind Ethereum's efficient committee attestations.
  • Merkle tree: A binary tree of hashes where each parent is the hash of its children — lets you prove a single leaf belongs to a huge dataset with only log(n) hashes (a Merkle proof), without revealing the rest.
  • Patricia trie (Merkle Patricia Trie): Ethereum's actual state data structure — a radix trie (efficient key lookups by shared prefixes) combined with Merkle hashing (so the whole state has one verifiable root hash: stateRoot).
  • Verkle tree: A proposed successor using vector commitments instead of plain hashing, producing dramatically smaller proofs — part of Ethereum's roadmap to enable stateless clients.
  • Public/private key + address generation: A private key (random 256-bit number) derives a public key via elliptic-curve multiplication; the address is the last 20 bytes of Keccak256(public key) — one-way at every step, so an address never reveals the key that controls it.

Networking

  • DevP2P: Ethereum-family chains' peer-to-peer networking stack — RLPx encrypted transport plus subprotocols (eth, and in XDPoS's case, an added XDPoS subprotocol for consensus messages).
  • Gossip protocol: New blocks/transactions/votes propagate by each node forwarding to a subset of its peers, who forward to theirs — no central broadcaster, and the network self-heals around outages.
  • Peer discovery / ENR: Nodes advertise an Ethereum Node Record (a signed, extensible record of IP, ports, and capabilities) so peers can find and validate each other without a central directory.
  • Bootnodes: Well-known, stable nodes whose only job is answering "who else is on this network" for new nodes joining — they hold no chain state and take no part in consensus (see Part IV).
  • JSON-RPC / HTTP-RPC / WebSocket: The standard client-facing API — HTTP for request/response calls, WebSocket for subscriptions (new blocks, pending transactions, logs) that push updates instead of polling.
  • Engine API: The CL↔EL local API described in Module 5 — conceptually a specialized, authenticated JSON-RPC namespace, not a public-facing one.
20

Execution Layer / EVM

  • EVM: A stack-based, 256-bit-word virtual machine every full node runs identically — determinism here is what lets thousands of independent nodes agree on the exact same resulting state.
  • Stack / memory / storage: Three separate data areas with very different costs — stack is cheap and ephemeral (per-call), memory is cheap-ish and ephemeral (per-call, grows quadratically in cost), storage is expensive and permanent (per-contract, persists on-chain forever).
  • Calldata: The read-only input data attached to a call — cheaper than memory to reference, and the primary way arguments reach a contract function.
  • ABI (Application Binary Interface): The encoding spec that turns a function call like transfer(address,uint256) into the raw bytes a contract's fallback dispatch logic recognizes (first 4 bytes = function selector).
  • Bytecode: The actual compiled opcodes stored at a contract's address and executed by the EVM — Solidity/Vyper source never runs directly, only this.
  • Contract creation: A transaction with an empty to field and "init code" as data — the EVM runs the init code once, and whatever it returns becomes the permanently-stored contract bytecode at the newly-derived address.
  • DELEGATECALL: Executes another contract's code in the caller's own storage/context — the foundation of upgradeable proxy patterns, and also a classic exploit vector if misused (a malicious "implementation" can rewrite the proxy's storage arbitrarily).
  • STATICCALL: Like a regular call but enforces read-only — any attempted state change inside it reverts the whole call, used to safely call untrusted code for view-only data.
  • CREATE2: Deploys a contract at an address computable in advance from (deployer, salt, init-code hash) rather than depending on the deployer's nonce — enables counterfactual deployment (an address can receive funds before the contract exists there).
21

Smart Contracts

  • Solidity: The dominant contract language — statically typed, compiles to EVM bytecode.
  • Inheritance / interfaces / libraries: Solidity supports OOP-style multiple inheritance (resolved via C3 linearization), interfaces for external-call type safety, and libraries for reusable, often delegatecall-embedded logic.
  • Modifiers: Reusable pre/post-condition wrappers on functions (e.g., onlyOwner) — sugar for common require-then-execute patterns.
  • Mappings / storage / memory keywords: Mappings are hash-table-like but only ever live in storage; the storage/memory/calldata keywords on reference types control whether a variable is a persistent pointer or a temporary copy — getting this wrong is a classic bug source.
  • Events: Declared with event, emitted with emit — compiled down to LOG opcodes, cheaper than storage specifically because logs aren't part of contract-readable state, only externally observable.
  • Assembly (Yul/inline): Direct low-level EVM opcode access from within Solidity, used when gas optimization or an operation Solidity doesn't expose natively is required.
  • Fallback / receive: receive() handles plain ETH transfers with empty calldata; fallback() handles calls that don't match any function selector (or any ETH transfer if receive is absent) — both are entry points attackers specifically probe.
  • Proxy / upgradeable contracts: Separates a stable proxy address (that users/contracts interact with) from swappable logic contracts via DELEGATECALL, so contract logic can be upgraded without changing the address or migrating storage.
  • Diamond pattern (EIP-2535): A proxy pattern that routes to many logic contracts ("facets") by function selector instead of just one, working around the 24KB contract size limit for very large systems.

DeFi

  • AMM (Automated Market Maker): Replaces an order book with a pricing formula (classically x*y=k) against a pooled reserve — anyone can trade against the pool at a price the formula sets, no counterparty matching needed.
  • DEX: A decentralized exchange built on an AMM (or on-chain order book) — trades settle directly via smart contract, no custodial intermediary.
  • Liquidity pool: The pooled reserve of two (or more) assets that an AMM trades against; depositors ("liquidity providers") earn a cut of trading fees.
  • Yield farming: Chasing the highest combined return across lending interest, trading fees, and bonus token incentives by moving capital between protocols.
  • Lending/borrowing: Overcollateralized loans against crypto assets (Aave, Compound-style) — no credit check possible on-chain, so the loan-to-value ratio and liquidation mechanism substitute for underwriting.
  • Flash loans: Borrow any amount with zero collateral, provided it's borrowed and repaid within the same transaction — if repayment (plus fee) fails, the entire transaction reverts as if it never happened, making default cryptographically impossible.
  • Impermanent loss: The value an LP loses (relative to just holding the two assets) when the pool's price ratio moves away from the ratio at deposit time — "impermanent" because it only becomes a realized loss if you withdraw while the prices are still diverged.
  • Stablecoins: Tokens pegged to an external value (usually USD) via fiat-backed reserves (USDC), over-collateralized crypto debt (DAI), or algorithmic mechanisms (historically fragile, see Terra/UST's 2022 collapse).
  • Oracles: The bridge that feeds real-world data (prices, in most DeFi cases) on-chain — a frequent attack surface, since manipulating the oracle can be cheaper than manipulating the actual market.

Layer 2

  • Rollups: Execute transactions off the main chain (L1) but post compressed transaction data (and a state commitment) back to L1, inheriting L1's security for data availability while scaling throughput.
  • Optimistic rollups: Assume state transitions are valid by default; anyone can submit a fraud proof during a challenge window (often ~7 days) to revert an invalid one. Examples: Arbitrum, Optimism, Base.
  • ZK rollups: Post a cryptographic validity proof (zk-SNARK/STARK) alongside every batch, proving correctness immediately — no challenge window needed, but proof generation is computationally heavier. Examples: zkSync, Starknet.
  • State channels: Two or more parties transact off-chain, only settling the final net state on-chain — fast and cheap, but limited to interactions among a fixed, known set of participants.
  • Plasma: An earlier scaling design using child chains anchored to L1 via periodic Merkle root commitments — largely superseded by rollups due to data-availability weaknesses.

Blockchain Security (Auditing)

  • Smart contract auditing: Combines manual line-by-line review, automated static/dynamic analysis, and often formal verification for high-value contracts.
  • Reentrancy: A contract makes an external call before updating its own state, letting the callee re-enter and drain funds using stale state — the exploit behind The DAO hack (2016).

  • Oracle attacks: Manipulating or front-running the price feed a contract trusts.
  • Formal verification: Mathematically proving a contract satisfies a specification, rather than just testing example cases.
  • Tooling: Slither (fast static analysis), Mythril (symbolic execution), Echidna (property-based fuzzing), Foundry's built-in fuzzing/invariant testing.

Part II

How XDC and XDPoS actually work

Every term from Part I now gets mapped onto a real, running, permissioned chain. XDPoS is a fork of go-ethereum, so most of the EVM/transaction/networking machinery from Part I applies unchanged — the entire divergence is concentrated in the consensus engine.

What is XDC?

XDC is the native token of the XinFin Network, a chain positioned for enterprise trade-finance and cross-border payment use cases — fast (2-second blocks), cheap, and with deterministic finality rather than PoW-style probabilistic settlement. Architecturally it's an EVM-compatible chain (so ordinary Solidity contracts, ERC-20/721 tokens, and standard tooling like MetaMask/ethers.js/Hardhat all work against it, per Part I Modules 20–25), but its consensus engine is not Ethereum's — it's XinFin's own, called XDPoS.

What is XDPoS?

XDPoS — XinFin Delegated Proof of Stake — is a consensus engine forked from go-ethereum's pluggable consensus.Engine interface (the same extension point go-ethereum used for its old Clique proof-of-authority engine). Instead of implementing PoW's Seal()/VerifySeal() logic, XDPoS implements a masternode round-robin proposer schedule with BFT-style voting layered on top. The "Delegated" part refers to how the validator set is chosen: coin holders vote (by staking XDC toward a candidate) for a fixed number of masternode operators, rather than every staker running their own validator the way Ethereum's permissionless model works.

Four properties define it in practice:

  • Fast, fixed block time — 2 seconds, because the proposer schedule is deterministic (no PoW-style race, no random-selection latency).
  • Epoch-based masternode rotation — the active masternode list is re-evaluated every epoch (900 blocks) based on current stake-weighted votes.
  • BFT-style finality (v2) — blocks are finalized by an explicit 2/3+ quorum certificate, not by waiting N confirmations and hoping.
  • Permissioned validator set — unlike Ethereum where anyone with 32 ETH can become a validator, only addresses elected into the masternode list (or, on a private network, hardcoded in genesis) may propose/sign blocks.

XDPoS v1 — how the original design worked

v1 is architecturally closer to Clique proof-of-authority than to a textbook BFT protocol. Masternodes take turns proposing blocks in a deterministic round-robin order derived from the sorted masternode list. Each block's extraData field is signed by the proposer, and every other masternode is expected to also sign ("second-sign") recent blocks as they pass — enough matching signatures within a window act as an informal, checkpoint-based confirmation rather than an explicit single-round quorum vote. Finality under v1 is closer to Nakamoto-style — a block gets safer the deeper it is and the more subsequent masternode signatures accumulate on top of it — rather than the instant, provable finality BFT protocols give (Part I, Module 6). This is why v2 exists: v1 gives you fast, cheap blocks, but not the hard safety guarantee an enterprise settlement use case wants.

Epoch mechanics common to both versions

  • Epoch = 900 blocks (~30 minutes at 2s blocks) — the boundary where the masternode list is recomputed from current votes.
  • Gap = 450 blocks — the masternode list for the next epoch is actually snapshotted gap blocks before the epoch boundary, not exactly at it. This exists so every masternode has a known, stable set to prepare for in advance — if the list were only known the instant the new epoch started, there'd be no time to safely hand off proposer duty without risking a stalled slot.
  • Reward checkpoint = 900 blocks — masternode rewards (10 XDC in the private devnet's genesis) are distributed once per epoch, not per block, keeping reward accounting cheap.

XDPoS v2 — the BFT redesign

v2 (introduced as a live network upgrade, activated at a configured v2 switch block in genesis/chain config — 0 means "BFT from genesis," which is how the private devnet is configured) replaces the informal second-signing scheme with an explicit, pipelined BFT protocol modeled on the same family as HotStuff/Tendermint: proposal → vote → quorum certificate → commit.

The v2 round, step by step

  1. Round starts: The masternode whose turn it is (round-robin over the current masternode list) is the leader for this round.
  2. Propose: The leader builds a block extending the highest quorum-certified (QC'd) block it knows about, and broadcasts it.
  3. Vote: Every other masternode validates the block and, if valid, signs and broadcasts a vote for it.
  4. Quorum Certificate (QC): Once votes from masternodes controlling ≥certThreshold (0.667, i.e. 2/3) of the masternode set are collected for that block, they're combined into a QC — a compact, verifiable proof that 2/3+ of the network agreed.
  5. Commit: Because each new block embeds the QC of its parent, once a block's child also reaches a QC, the parent is considered committed/finalized — the same two-hop finalization logic as Casper FFG (Part I, Module 8), just applied per-block instead of per-epoch-checkpoint. This is why XDPoS v2 finality is measured in seconds, not minutes.
  6. Timeout path: If the leader fails to propose in time (offline, network partition), masternodes instead broadcast signed timeout messages. Once ≥2/3 of masternodes agree the round timed out, a Timeout Certificate (TC) is formed, the round advances, and the next masternode in the schedule becomes leader — this is the liveness fallback so one bad leader can't stall the chain indefinitely.

Masternode Election — how the validator set is actually chosen

On a public XDC network, the masternode set isn't fixed — it's the outcome of an on-chain vote run through a system smart contract (deployed at a well-known address, conventionally referenced in this guide as the "Masternode/Validator contract"). Any address can register as a candidate by staking a minimum amount of XDC; any XDC holder can then "vote" for a candidate by locking additional XDC behind them (this is delegated staking exactly as described in Part I, Module 4). At each epoch boundary (minus the gap, see above), the contract's current vote tallies are read, the top addresses (up to a configured maximum — 108 on the public network) become the masternode set for the next epoch, and anyone who drops out of the top ranks stops proposing/voting.

On a private/consortium deployment like the pvt-xdpos devnet, this election machinery still exists in the code, but it's short-circuited: the initial masternode set is simply hardcoded into the genesis extraData field (Part VI covers this byte-for-byte), so there's no need to wait for votes to accumulate before the chain can start producing blocks. The contract is still deployed and could be used to change the set later, but a 4-masternode private devnet typically never bothers.

Penalty & comeback list

Masternodes that miss too many proposal turns or get caught equivocating are added to a penalty list and temporarily excluded from the round-robin schedule (their slot is skipped) without a full re-election — a lighter-weight version of Ethereum's inactivity penalties (Part I, Module 14) that doesn't require slashing to be economically meaningful on a small, mostly-trusted masternode set.

Part III

What Puppeth is, and what it actually does

You asked "what is puppet" — it's Puppeth, and it's not a smart contract tool or a testing framework. It's a genesis-configuration wizard.

Puppeth, explained properly

Puppeth is a command-line interactive wizard shipped inside go-ethereum's source tree (and inherited by XDPoSChain, since it's a go-ethereum fork) whose entire job is to generate a correct genesis.json — plus, in the upstream go-ethereum version, optional Docker/systemd deployment scaffolding for a new network. Without it, launching a private network means hand-writing a genesis file that must get several genuinely fiddly things exactly right: the consensus config block's nested fields, the extraData byte layout encoding your initial signer/masternode list, and — for XDPoS specifically — the pre-deployed system contract bytecode and storage slots (the masternode/validator contract, block-signer contract, randomize contract, and multisig wallets). Get any single byte of that wrong and every node that inits from it computes a different state root, which means the network can never agree on genesis at all (this is exactly why Part VI stresses "genesis must be byte-identical everywhere").

Practically: you answer a sequence of prompts (network name, consensus engine, block period, epoch length, reward amount, initial signer addresses, pre-funded accounts, chain ID), and Puppeth assembles a genesis.json that already has the correct shape for whichever consensus engine you picked — Clique, Ethash, or, in the XinFin fork, XDPoS.

Part IV

Node types — properly detailed

Every role below runs the exact same XDC binary — the difference is entirely which flags are set, whether a signing keystore is unlocked, and what ports/APIs are exposed. This is what "detailed nodes" means concretely.

4.1 — Bootnode (discovery-only)

A bootnode does not execute the EVM, hold state, sign blocks, or sync the chain at all. Its only function is Kademlia-style peer discovery — helping new nodes find existing peers via signed ENR records over UDP.

  • Binary: bootnode, built alongside XDC (make bootnode).
  • Key: boot.key — a raw secp256k1 key that derives the bootnode's node ID (its P2P identity), not an account/wallet.
start-bootnode.sh
bootnode -nodekey ./bootnode/boot.key -addr ":30310" -verbosity 5

Output is an enode://<nodeid>@<ip>:30310 URI that every other node lists as a bootnode/static peer. Port: UDP 30310 only (no TCP RPC, no sync traffic). It's stateless — restarting with the same key reuses the same node ID, and if it goes down after peers already know each other, the network keeps running fine; it's only needed for discovering new peers.

Ports: 30303 TCP/UDP (P2P), 8501 HTTP-RPC, 8502 WS-RPC, plus the local XDC.ipc socket. Only validator nodes are exposed to penalty-list risk — missing a proposal turn or double-signing gets an address flagged and temporarily/permanently dropped from the masternode schedule.

4.3 — Full Node (non-validator / observer)

Syncs and independently validates the entire chain, keeps full state, serves RPC — but never proposes blocks (no keystore unlocked). Used for dApp backends, explorers, wallets, or pure redundancy.

The only real difference from §4.2: no --mine, no --unlock, no --etherbase. It still fully verifies every block's quorum certificate — it just never produces one.

4.4 — RPC / Gateway Node

A full node purpose-built to sit behind a load balancer and absorb public JSON-RPC/WebSocket traffic, keeping validators off the open internet entirely.

  • Usually --gcmode archive so historical "as of block N" queries (eth_getBalance, eth_call) work.
  • --http.corsdomain plus an nginx/HAProxy layer in front for rate limiting.
  • --txpool.pricelimit tuned against spam.
  • Never has --mine or an unlocked key — a compromised RPC node should never be able to sign a block.

4.5 — Standby / Backup Validator Node

A hot-spare mirroring a validator's datadir/keystore, kept with mining disabled (or the process stopped) so two live copies of the same key never sign simultaneously — XDPoS treats that as equivocation, exactly the same penalty-triggering event as a malicious double-sign (Part II). Failover between primary and standby must be mutually exclusive, either manually or via an orchestrator that guarantees only one is ever --mine-active at a time.

4.6 — Node-to-node connection lifecycle

  1. Init: XDC init private-genesis.json --datadir <dir> computes the genesis state root from alloc+config and writes it into that node's local LevelDB (see Part VI for exactly what this computes).
  2. Identity load: The node generates or loads its nodekey (P2P identity — separate from any validator signing keystore) at <datadir>/geth/nodekey.
  3. Discovery: Dials the bootnode's enode URI, receives peer ENRs, and populates its Kademlia peer table.
  4. Handshake: RLPx encrypted transport handshake, then the eth/XDPoS subprotocol handshake exchanging genesis hash, chain ID, and current head — a mismatched genesis hash gets the peer dropped immediately, which is exactly the failure mode a wrong genesis byte produces.
  5. Sync: Requests headers/bodies from peers, replays state transitions until eth.blockNumber matches the network head.
  6. Gossip: Once synced, new blocks and (for validators) votes/timeout messages propagate peer-to-peer, independently re-validated at every hop before relaying.
  7. Consensus (validators only): On its round-robin turn, the node assembles a block from its mempool, signs it, and broadcasts — peers collect 2/3+ votes into a QC for finality.

Security notes across node types

  • Only validator nodes should ever have an unlocked key + --mine; every other role is strictly read/relay.
  • password.txt and keystore/ should be filesystem-permissioned (chmod 600) and never leave the host unencrypted, including in backups.
  • Two live processes with the same unlocked key (primary + standby both active) is the single most common cause of accidental self-penalty in devnets — treat it as equivalent to malicious equivocation from the protocol's point of view.
  • Bootnodes and RPC nodes are safe to expose publicly since neither holds signing power; validator P2P ports are typically firewalled to known peer IPs only.

Part VI

Genesis — every field, in detail

The genesis block is block 0: no parent, no prior state, the single fixed point every node must independently compute the exact same hash for. Below is every field that appears in private-genesis.json, what it means, and what actually happens when you run XDC init against it.

6.1 — Top-level fields

config

A nested object carrying every chain-rule and consensus parameter — chain ID, EVM hard-fork activation blocks (homestead, EIP-150, etc., inherited from go-ethereum's fork-numbering system), and the XDPoS-specific sub-object (period, epoch, reward, v1/v2 fields — all of Part II §xdpos-v1/v2). This is the single most important object in the file: every node must derive an identical internal chain configuration from it.

chainId

9876 for this private devnet. Embedded in every transaction signature (EIP-155, Part I Module 17) specifically so a transaction signed for this private network can never be replayed on public XDC mainnet or any other chain sharing similar tooling — and vice versa.

nonce

A PoW leftover field (used by miners to find a valid hash) — meaningless under XDPoS since there's no mining puzzle, conventionally left at its default/zero value.

timestamp

Unix time the genesis block was authored. Every subsequent block's timestamp must be strictly greater than its parent's, so this is the floor the entire chain's clock is built on.

extraData

The field carrying the initial masternode signer list. Structurally (inherited from Clique's convention, which XDPoS reused): 32 bytes of arbitrary "vanity" data, followed by the concatenated 20-byte addresses of every initial signer, followed by 65 bytes reserved for a seal signature (unused/zeroed at genesis, since genesis itself is never "signed" by a proposer — it's simply agreed upon by everyone running the same file). For this devnet, that's 32 bytes vanity + 4 × 20 bytes (validator1..4) + 65 zero bytes.

gasLimit

4,700,000 in this devnet — the maximum gas the very first block (and, as a starting point, blocks shortly after) may consume; later blocks can adjust this within protocol-defined bounds as usage changes (Part I, Module 16).

difficulty

A PoW-era field, set to a nominal constant (commonly 1) in PoS/PoA/BFT-style private networks since there's no proof-of-work puzzle to size a target against — it's kept only because the block header format is shared with PoW go-ethereum and can't simply omit the field.

mixHash

Another PoW artifact (part of Ethash's proof verification) — zero/empty in an XDPoS genesis since there's no hash puzzle being verified.

coinbase

The default block-reward beneficiary field on the header — at genesis specifically, there's no reward to pay (block 0 isn't "proposed" by anyone), so it's conventionally the zero address.

alloc

The pre-funded account table and — critically for XDPoS — the pre-deployed system contracts. This is where the chain's starting state lives; everything else in the genesis file configures rules, but alloc is actual state.

number

Always 0 — this is, by definition, the block-number-zero block.

gasUsed

0 — no transactions execute in the genesis block itself; all its state comes directly from alloc, not from executing transactions.

parentHash

The zero hash (0x00...00) — by definition, genesis has no parent.

baseFeePerGas

Null in this network, since it predates/doesn't enable an EIP-1559-style base-fee market (Part I, Module 16) — fees here are flat, not burned.

6.2 — What's actually inside alloc

Beyond ordinary pre-funded validator accounts (each masternode address gets a large starting balance so it has gas to operate from block 0 without needing an external faucet), XDPoS genesis files pre-deploy several system contracts directly as raw bytecode + storage slots at fixed, conventional addresses — this is the part Puppeth (Part III) exists specifically to get right, since hand-writing correct deployed bytecode and storage layout by hand is extremely error-prone:

Conventional address suffixContractRole
0x...88Validator / Masternode contractTracks candidate registration, stake-weighted votes, and the current masternode list (Part II §xdpos-masternodes).
0x...89Block signer contractRecords which masternode signed which block — the on-chain bookkeeping v1's "second-signing" checkpoint scheme (and v2's QC logic) reads from.
0x...90Randomize contractSupplies on-chain randomness used in masternode-related scheduling/selection logic.
0x...68Foundation multisig walletHolds/manages foundation-controlled funds from genesis.
0x...99Team multisig walletHolds/manages team-controlled funds from genesis.

Because these are pre-deployed (bytecode written directly into alloc, not deployed by a genesis transaction — recall gasUsed is 0), they exist and are callable from block 1 onward with zero deployment lag, which matters for a masternode contract that the consensus engine itself needs to query starting from the very first epoch.

6.3 — From file to running network: what XDC init actually computes

  1. Puppeth or hand-crafting produces private-genesis.json containing everything in §6.1–6.2.
  2. The file is copied, byte-for-byte identical, to every node that will join the network — bootnode excluded, since it never touches chain state.
  3. Running XDC init private-genesis.json --datadir <dir> on each node: parses the file, builds the initial state trie from alloc (every account balance and every system contract's bytecode + storage becomes a leaf in a fresh Merkle Patricia Trie, Part I Module 18), computes the resulting state root hash, assembles the full genesis block header (using that state root plus the other top-level fields), and writes both the header and the trie into that node's local LevelDB.
  4. The genesis block hash (0xc1d1e1195f67cc66bc6e2b169f02675a8488e4776815d02afe2251bc660004f3 for this devnet) is simply the hash of that fully-assembled header — a deterministic function of every single field above. Change one byte anywhere in alloc or config, and this hash changes completely.
  5. When nodes connect (Part IV §4.6, step 4), the very first thing the eth/XDPoS subprotocol handshake checks is genesis hash equality — a mismatch means the peer computed a different state root from a different (or subtly corrupted) genesis file, and the connection is refused outright. This is the actual failure mode "genesis must be identical everywhere" protects against: it's not a style preference, it's a hard equality check baked into the P2P handshake.

Why this can't be fixed after the fact

Once even one node has already run XDC init against a slightly different genesis file, there is no "sync it back" — its local genesis state root is permanently baked into block 0 of its local chain. The only fix is wiping that node's datadir and re-running XDC init with the correct, matching file.
